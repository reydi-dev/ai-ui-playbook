# ۰۲ · اجرای یک مرحله

بعد از [شناخت تسک](./task-scope)، فقط یک بخش از برنامه تأییدشده را اجرا کن. هدف این نیست که ایجنت در یک نوبت تمام فلو را بازنویسی کند.

<div class="chapter-note">

**خروجی این فصل:** یک بخش قابل اجرا، با ظاهر جدید و رفتار حفظ‌شده؛ آماده مقایسه و تست، نه آماده تأیید خودکار.

</div>

## ورودی‌های لازم

- مرحله انتخاب‌شده، مسیر صفحه و لینک دقیق فریم آن.
- نتیجه بررسی اولیه و تصمیم‌های تأییدشده درباره ابهام‌ها.
- دستور اجرای پروژه و قواعد کامپوننت‌ها و تست‌ها.
- وضعیت Git: برنچ تسک و تغییرات موجودی که نباید دست بخورند.

## اتصال و خواندن طرح

از ایجنت بخواه با ابزار اتصال به فیگما، نام و اندازه فریم و بخش‌های داخل آن را گزارش کند. این کار مشخص می‌کند واقعاً طرح هدف را می‌بیند. رمز حساب یا توکن را در پرامپت نگذار؛ اتصال را از تنظیمات ابزار مربوط انجام بده.

اگر ابزار خطای دسترسی یا محدودیت داد، لینک همان نود و دسترسی حساب را بررسی کن. اگر اتصال ممکن نبود، تصویر با وضوح مناسب و SVG آیکن‌های لازم جایگزین موقت‌اند؛ جزئیات نامشخص نباید «دقیقاً مشابه فیگما» گزارش شوند.

برای فلو بزرگ ابتدا فهرست فریم‌ها را بگیر، سپس فقط فریم مرحله جاری را با جزئیات بخوان. نام یک فریم به‌تنهایی برای تشخیص حالت آن کافی نیست؛ حالت باز و بسته، خطا و موفقیت را جدا مشخص کن.

## پرامپت آماده

```text
مرحله جاری: [عنوان و خروجی مورد انتظار]
مسیر صفحه: [مسیر]
فریم هدف: [لینک]
نمایش هدف: [دسکتاپ یا موبایل و عرض فریم]
تصمیم‌های تأییدشده: [خلاصه]
قواعد و دستور اجرای پروژه: [مسیر فایل راهنما یا دستور]

ابتدا وضعیت Git و فایل‌های مرتبط همین مرحله را بررسی کن.
تغییرات موجود من را حفظ کن.
با ابزار فیگما، خود فریم و ساختار والد و فرزند آن را بخوان.
فقط همین مرحله را پیاده‌سازی کن.

از کامپوننت‌ها، فونت‌ها و آیکن‌های موجود پروژه استفاده کن.
اگر آیکن دقیق در فیگما موجود است، امکان استفاده از همان دارایی را بررسی کن؛
اگر با قواعد پروژه ناسازگار است قبل از جایگزینی تصمیم بگیرم.
رفتار، اعتبارسنجی، رویدادها، API و وضعیت فرم را حفظ کن.
کامپوننت پایه را بدون تأیید تغییر نده.
برای موبایل، تا جای ممکن همان کامپوننت را واکنش‌گرا کن.
اگر طرح نیاز به تغییر منطق دارد، اختلاف و پیشنهاد را قبل از آن تغییر گزارش کن.

پس از اجرا:
- اختلاف ظاهری باقی‌مانده را خودت بررسی کن.
- بررسی‌های متناسب و مجاز پروژه را انجام بده.
- خلاصه فایل‌ها، تغییر رفتار احتمالی، تست‌های انجام‌شده و انجام‌نشده را بده.
فعلاً کامیت یا پوش نکن و سراغ مرحله بعد نرو.
```

## تصمیم درباره تمیز کردن کد

پاک‌سازی را به کد همین بخش محدود کن. استخراج کامپوننت وقتی مفید است که تکرار یا پیچیدگی را کم کند؛ صرفاً کوتاه‌شدن فایل دلیل کافی نیست.

پیش از ادغام دو فرم، تفاوت اعتبارسنجی، ارسال داده، رویدادها و مصرف‌کننده‌ها را بررسی کن. شبیه‌بودن ظاهر تضمین نمی‌کند منطق آن‌ها یکسان است. تغییر مشترک پرریسک را با مدیر فنی مطرح کن و در صورت نیاز به تسک جدا منتقل کن.

## چک‌لیست بررسی

- محدوده تغییرات از مرحله جاری فراتر نرفته است.
- صفحه از مسیر واقعی برنامه باز می‌شود.
- داده تست واقعیِ مجاز جایگزین متن‌های نمایشی شده است.
- نام فیلدهای API و شرایط فعال‌شدن دکمه‌ها ناخواسته تغییر نکرده‌اند.
- تغییرات مشترک و اثرشان شناسایی شده‌اند.
- ایجنت روشن گفته کدام بررسی را واقعاً اجرا کرده است.

## شرط ادامه

بخش باید قابل اجرا باشد. سپس [مقایسه ظاهری](./visual-review) و [تست رفتار](./testing) را انجام بده؛ «پیاده‌سازی شد» به معنی «تأیید شد» نیست.

## مصرف کمتر توکن

برنامه تأییدشده و تصمیم‌ها را خلاصه بده. برای اصلاح فاصله یک دکمه، کل فایل فیگما و تمام کامپوننت‌های پروژه را دوباره وارد گفتگو نکن.
