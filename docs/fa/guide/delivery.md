# ۰۵ · کامیت و تحویل

هر بخش تأییدشده باید یک نقطه بازگشت روشن داشته باشد. در پایان تسک، مدیر فنی باید بتواند تغییر را از روی برنچ، توضیح درخواست ادغام و روش تست بررسی کند.

<div class="chapter-note">

**خروجی این فصل:** کامیت‌های مشخص برای بخش‌های تأییدشده و یک درخواست ادغام قابل بررسی در پایان تسک.

</div>

## ورودی‌های لازم

- برنچ جدا برای تسک و برنچ مقصد مطابق روال تیم.
- نتیجه بررسی ظاهری و رفتاری هر بخش.
- فهرست تصمیم‌های تأییدشده و محدودیت‌های باقی‌مانده.
- diff نهایی و فهرست فایل‌های متعلق به تسک.

## قبل از هر کامیت

وضعیت Git و diff را ببین. تغییرات نامرتبط خودت یا دیگران نباید همراه تسک ثبت شوند. فایل‌های تولیدی، اسرار و اطلاعات واقعی تست را وارد کامیت نکن. تغییرات unrelated را هم برای تمیزشدن وضعیت Git حذف نکن.

در روال این راهنما، پیام کامیت فارسی و روشن است:

- «هماهنگ‌سازی کارت‌های انتخاب سرویس در دسکتاپ»
- «اصلاح چینش دریافت‌ها در موبایل»
- «حفظ اطلاعات فرم هنگام برگشت به مرحله قبل»

پیام‌هایی مثل «اصلاحات» یا «آپدیت UI» مشخص نمی‌کنند چه چیزی تغییر کرده است.

## پرامپت کامیت بخش تأییدشده

```text
بخش [نام بخش] را بررسی و تأیید کردم.
وضعیت Git و diff را دوباره بررسی کن.
فقط تغییرات متعلق به این بخش را stage و commit کن.
تغییرات نامرتبط را حفظ کن؛ فایل حساس یا خروجی تولیدی وارد کامیت نشود.
پیام فارسی پیشنهادی: [پیام مشخص]
اگر یک فایل شامل تغییرات مخلوط و غیرقابل تفکیک است، قبل از stage کردن گزارش کن.
بعد از کامیت، شناسه کامیت و وضعیت باقی‌مانده را بده.
فعلاً پوش نکن.
```

## پایان تسک و درخواست ادغام

در GitHub نام آن Pull Request و در GitLab معمولاً Merge Request است. در این راهنما هر دو را «درخواست ادغام» می‌نامیم.

قبل از ساخت درخواست، کل مسیر را یک بار مطابق محدوده تغییرات بررسی کن؛ ممکن است بخش‌ها جداگانه درست باشند اما انتقال بین آن‌ها خراب شده باشد. دسکتاپ و موبایل و مصرف‌کننده‌های مشترک مهم را فراموش نکن.

مدیر در روال نمونه، برنچ را اجرا و جامع بررسی می‌کند. ارسال اسکرین‌شات اجباری نیست؛ توضیح روش بازتولید و تست باید برای بررسی نسخه اجرایی کافی باشد. تا تکمیل بررسی، خودکار merge نکن.

## قالب توضیح درخواست ادغام

```text
عنوان: [نتیجه مشخص تغییر]

مسئله و نتیجه:
[قبلاً چه اتفاقی می‌افتاد و اکنون چه می‌شود]

محدوده:
[صفحه‌ها، حالت‌ها و دسکتاپ/موبایل]

تغییر منطق یا قرارداد:
[ندارد، یا شرح دقیق تغییر تأییدشده]

روش بررسی:
۱. [مسیر شروع و شناسه سناریوی تست داخلی]
۲. [اقدام]
۳. [نتیجه مورد انتظار]

اعتبارسنجی انجام‌شده:
[تست یا سناریو + نتیجه واقعی]

محدودیت‌ها و بررسی‌های انجام‌نشده:
[شرح صریح یا «ندارد»]

تصمیم‌های طرح:
[استثناهای تأییدشده، در صورت وجود]
```

در ریپوی عمومی از شناسه‌های واقعی، لینک خصوصی فیگما و تصاویر داده داخلی استفاده نکن. برای اطلاعات لازم به روش دسترسی داخلی تیم اشاره کن.

## چک‌لیست و شرط پایان

- کامیت‌های هر بخش روشن و مرتبط‌اند.
- برنچ مقصد و محدوده diff درست است.
- بررسی‌های انجام‌نشده پنهان نشده‌اند.
- روش تست برای فردی خارج از گفتگو قابل فهم است.
- پاک‌سازی کد، API یا کامپوننت مشترک اثر نامشخص ندارد.
- درخواست ادغام برای بررسی مدیر آماده است.

پوش، ایجاد درخواست ادغام و ادغام نهایی سه اقدام متفاوت‌اند. در پرامپت مشخص کن کدام اقدام را می‌خواهی و کدام هنوز باید منتظر بررسی بماند.

## مصرف کمتر توکن

توضیح درخواست ادغام را از نتیجه نهایی و شواهد تست بساز. تاریخچه رفت‌وبرگشت‌ها و راه‌حل‌های کنارگذاشته‌شده را تنها وقتی بیاور که برای فهم تصمیم نهایی لازم‌اند.
